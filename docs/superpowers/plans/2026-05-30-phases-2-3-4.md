## Phase 2 — Buku Tamu (attendance ledger)

**Goal.** A "Buku Tamu" tab in the dashboard that lists every guest who
attended the wedding. Auto-populates from RSVPs (status "yes"), supports
adding walk-ins via search-match against the existing `guests` table.
**Gate this tab to `plan='premium'`** — basic plan does not get it.

### Data model

New table:

```sql
CREATE TABLE attendances (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  invitation_id uuid NOT NULL REFERENCES invitations(id) ON DELETE CASCADE,
  guest_id      uuid REFERENCES guests(id),              -- nullable: null for RSVP-only entries
  rsvp_id       uuid REFERENCES rsvps(id),               -- nullable: null for pure walk-ins
  name_enc      text NOT NULL,                           -- encrypted in Phase 3, plaintext for now
  guest_count   int NOT NULL DEFAULT 1 CHECK (guest_count BETWEEN 1 AND 20),
  source        text NOT NULL CHECK (source IN ('rsvp','walkin')),
  note_enc      text,                                    -- encrypted in Phase 3
  arrived_at    timestamptz,                             -- nullable: set on check-in
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_attendances_invitation ON attendances(invitation_id, created_at DESC);
CREATE UNIQUE INDEX idx_attendances_rsvp_unique ON attendances(rsvp_id) WHERE rsvp_id IS NOT NULL;
CREATE UNIQUE INDEX idx_attendances_guest_unique ON attendances(invitation_id, guest_id) WHERE guest_id IS NOT NULL;

ALTER TABLE attendances ENABLE ROW LEVEL SECURITY;
-- service-role only (matches guests table convention)
```

Notes on the unique indexes:
- `rsvp_id` unique → an RSVP creates exactly one attendance row.
- `(invitation_id, guest_id)` unique → a walk-in for a given invited guest
  can only be added once (idempotent).

### Auto-create from RSVP

In `src/app/api/rsvp/route.ts`, after the successful insert into `rsvps`,
also insert a matching `attendances` row when `attending === true`. The
two writes can be a single Supabase RPC or two sequential service-role
inserts (transactional consistency is not critical here — duplicate
prevention is handled by the unique index).

```ts
// pseudo
if (rsvp.attending) {
  await admin.from('attendances').insert({
    invitation_id, rsvp_id: rsvp.id, guest_id: null,
    name_enc: rsvp.guest_name,            // will be ciphertext after Phase 3
    guest_count: rsvp.guest_count,
    source: 'rsvp',
    note_enc: rsvp.message,
  }).onConflict?.()  // or rely on unique index
}
```

### Walk-in flow (dashboard "+ Tambah Tamu Datang")

UI is a small dialog inside the new tab:

1. **Search input** (typeahead). On each keystroke (debounced ~200ms),
   query the `guests` table for the current `invitation_id` and return
   matches via fuzzy match on `name_enc` (decrypt server-side, then
   case-insensitive substring or trigram match). Return at most ~10 hits.
2. **Result list**: show name, group_label, masked phone. Couple picks
   one row.
3. **Guest count + optional note** field, then "Simpan".
4. Server action `addWalkInAttendance({ invitationId, guestId, count, note })`:
   - Verify the `guestId` belongs to `invitationId` (security check).
   - Insert into `attendances` with `source='walkin'`, `guest_id=guestId`,
     `arrived_at=now()`. Unique index protects against double-add.
5. If the search finds zero matches → "Tamu ini tidak ada di daftar
   undangan. Tambahkan dulu di tab Tamu." Walk-ins not in `guests` are
   rejected by design.

## Phase 3 — Tier-1 Encryption

**Goal.** Apply the AES-256-GCM pattern from `src/lib/guests/crypto.ts`
to RSVPs, gift confirmations, attendances, and selected paths in
`invitations.config`. Keep `owner_email`, couple's name, slug, plan, and
template_id plaintext (operator needs them for tracking + URLs).

### Key strategy (user picked "simple")

- Single env var `APP_ENCRYPTION_KEY` (32 bytes, base64).
  Generate: `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`.
- Reuse `src/lib/guests/crypto.ts` directly — its helpers
  (`encryptField` / `decryptField`) already accept a key param. Switch
  to a shared key getter `getAppEncryptionKey()` that reads
  `APP_ENCRYPTION_KEY`. Existing `GUESTS_ENCRYPTION_KEY` can either be
  retired (re-encrypt guests rows under the new key) or kept as a
  per-domain key. Recommended path: keep both keys, just add the new one
  for the new domains. Don't re-encrypt guests data.

### Tables to encrypt

| Table              | Plaintext now           | Encrypted after Phase 3                          |
|--------------------|-------------------------|--------------------------------------------------|
| `rsvps`            | `guest_name`, `message` | `guest_name_enc`, `message_enc` (drop plaintext) |
| `gift_confirmations` | `guest_name`, `amount`, `message` | `guest_name_enc`, `amount_enc`, `message_enc` |
| `attendances`      | `name_enc`, `note_enc`  | (already named `_enc` in Phase 2 schema — start encrypting writes/reads) |
| `invitations.config` | freeform JSONB        | selective sub-paths (see below)                  |
| `invitations.owner_email` | plaintext         | **stays plaintext** (per user: needs to track who bought) |

Migration shape (illustrative):

```sql
ALTER TABLE rsvps
  ADD COLUMN IF NOT EXISTS guest_name_enc text,
  ADD COLUMN IF NOT EXISTS message_enc    text;
-- backfill via node script, then:
ALTER TABLE rsvps ALTER COLUMN guest_name_enc SET NOT NULL;
ALTER TABLE rsvps DROP COLUMN guest_name;
ALTER TABLE rsvps DROP COLUMN message;
```

### invitations.config selective encryption

Encrypt these JSON paths (anywhere they appear, including inside
`sections[].props`):

- `accounts[].number`
- `accounts[].name`
- `whatsappNumber`
- `email`
- `phone`

Keep plaintext: `coupleName`, `brideName`, `groomName`, `eyebrow`,
`tagline`, headings, body text (per user: "couple name biarkan").

Implementation: server-side serializer (e.g.
`src/lib/payments/...` or new `src/lib/config-crypto.ts`) with two
functions, `encryptConfig(config)` and `decryptConfig(config)`. Walks
the tree recursively, encrypts string values at known sensitive keys.
A path marker (e.g. wrapping the ciphertext in `{ enc: '...' }`) makes
encrypt/decrypt idempotent and lets future readers detect already-
encrypted nodes.

Wire-up:
- Editor save (`PUT /api/invitation/[slug]/config`): `encryptConfig`
  before writing to DB.
- All reads (`page.tsx`, dashboard `EditorRoot`'s `initialConfig`):
  `decryptConfig` before passing to the renderer.

### Backfill

`scripts/encrypt-existing-data.mjs`:
1. For each table with plaintext → ciphertext migration, read all rows,
   encrypt with the new key, write back. Idempotent (skip rows where
   `_enc` column already populated and plaintext column NULL/dropped).
2. For `invitations.config`, walk every row and re-save the config
   through `encryptConfig`.

Run order: encrypt-then-migrate (write `_enc` first; then DROP plaintext
column after verifying every row is migrated).

- `supabase/migrations/2026-05-31_encrypt_tier1.sql` (new)
- `src/lib/crypto/app.ts` (new — shared key getter + reuse `guests/crypto.ts` helpers)
- `src/lib/crypto/config.ts` (new — encryptConfig / decryptConfig for JSONB)
- `src/app/api/rsvp/route.ts` (encrypt on write)
- `src/app/api/gift/route.ts` (encrypt on write)
- `src/app/[template]/[slug]/dashboard/RsvpsTab.tsx` (decrypt on read)
- `src/app/[template]/[slug]/dashboard/GiftsTab.tsx` (decrypt on read)
- `src/app/[template]/[slug]/dashboard/GuestbookTab.tsx` (decrypt on read)
- `src/app/[template]/[slug]/dashboard/page.tsx` (decrypt config before passing down? actually pass through, decrypt happens in EditorProvider load)
- `src/editor/EditorProvider.tsx` (or wherever initialConfig enters — decrypt there)

### Acceptance

- A direct DB dump of `rsvps` / `gift_confirmations` shows ciphertext
  only for sensitive fields.
- Dashboard tabs still show plaintext guest names + amounts.
- Editor still loads + saves config without errors.

  encrypted paths; structure (sections array, types, planet keys)
  remains plaintext.

- Tampered ciphertext throws on decrypt (AES-GCM authTag).

## Phase 4 — Performance Optimization

**Goal.** User reported the app feels slow. Diagnose, then fix the
top offenders.

### Profiling first (don't guess)

1. Build production locally: `npm run build && npm start`.
2. Lighthouse on key routes: `/`, `/templates`, `/solary/demo-solary`,
   `/<template>/<slug>/dashboard` (logged in).
3. Chrome DevTools Performance tab: record a cold load + a couple of
   interactions. Note the longest tasks, big bundles, slow XHRs.
4. `@next/bundle-analyzer` — install + add `next.config.js` plugin.
   Run `ANALYZE=true npm run build` and look for fat bundles.
5. Server-side: add a thin timing log in `src/app/[template]/[slug]/page.tsx`
   and `dashboard/page.tsx` to see DB query time vs render time.

### Suspected hot paths (validate with profiling)

| Path | Likely cost |
|---|---|
| `/solary/<slug>` | Three.js scene boot (`mountGalacticScene`), heavy starfield, Lenis init, motion |
| `dashboard/page.tsx` | 4 parallel admin queries (rsvps, gifts, notes, guests) + RSC fan-out |
| `EditorRoot` mount | Lazy section imports + Suspense waterfall + iframe preview |
| `templates/page.tsx` | New DB query (`getAllTemplatePlans`) — verify caching |
| `middleware` | Now runs on `/<template>/<slug>` too (added in 5b82324) — measure overhead |

### Wins to try (in roughly cheapest-first order)

1. **Memoize `getTemplatePlans` / `getAllTemplatePlans`** with
   `next/cache` (`unstable_cache`). Prices change rarely; cache for
   ~60s with tag invalidation on update.
2. **`next/image` everywhere** — currently many `<img src=picsum/...>`.
   Convert to `<Image>` with proper `sizes` and `priority` for hero
   images. Add `images.remotePatterns` for `picsum.photos` + Supabase
   Storage in `next.config.js`.
3. **Lazy-load Solary's Three.js scene** — already `dynamic({ssr:false})`
   at Shell, but the scene boots immediately on mount. Defer
   `mountGalacticScene` until after first paint (idle callback or
   intersection observer on the opening section).
4. **Reduce `'use client'` surface** in the editor — `FieldEditor`,
   `SectionList`, `SectionRow` are all client. Where possible, render
   the section labels / static parts on the server.
5. **Cache RSC fetches** in dashboard — use `unstable_cache` for the
   guests / notes queries that don't change per-request inside one tab
   session.
6. **Bundle splits** — the planet sections + Three.js push the Solary
   bundle large. Split per-section dynamic imports beyond Shell, or
   tree-shake unused Three modules.
7. **Compress middleware payload** — middleware currently runs on
   `/<template>/<slug>` (recent matcher addition). Audit its cost; if
   substantial, narrow the matcher to authenticated-only paths and find
   another mechanism for owner-preview session refresh.
8. **Suspense boundaries** around heavy sections in EditorRoot so the
   page LCP isn't blocked by lazy chunks.
9. **CDN-cache static template assets** — fonts, thumbnails, audio.

### Acceptance

- Lighthouse mobile score on `/` and `/templates` ≥ 85 perf.
- `/solary/demo-solary` time-to-first-paint < 2s on a fresh load.
- Dashboard TTI < 2s after login.
- No regression on the rest of the test suite or build.
